Оптимальный пайплайн на август 2026 — **SVT-AV1 (libsvtav1 в FFmpeg), preset 6, CRF 24–28, 10-bit, аудио Opus 96–128 kbps**. Это даёт визуально прозрачное качество при файле на 40–55 % меньше, чем у H.264, и ощутимо меньшем, чем у x265, при вменяемом времени кодирования.【turn0search1】【turn0search11】

## Почему именно SVT-AV1

Аппаратные AV1-энкодеры (NVENC AV1 на RTX 40/50, Intel QSV Arc, AMD AMF) кодируют в сотни раз быстрее, но уступают 15–18 пунктов BD-rate программному SVT-AV1 — то есть при том же качестве файл получается заметно тяжелее. Измерения 2026 года показывают: на одном и том же контенте SVT-AV1 preset 6 экономит ≈55 % битрейта против x264 medium при скорости 11 fps, тогда как NVENC AV1 p7 — ≈40 % при 480 fps. Разрыв между «самым быстрым AV1» (NVENC) и «самым эффективным» (SVT-AV1 preset 2, −58 %) — 18 пунктов по BD-rate только за счёт выбора энкодера и пресета.【turn0search11】

SVT-AV1 работает в 2–5 раз быстрее libaom при почти идентичном качестве, а его пресет 6 по скорости сопоставим с x265 slow, но заметно эффективнее.【turn0search1】【turn0search17】

## Модуль 1: Быстрый CPU-пайплайн (золотая середина)

Для большинства задач — оптимальный баланс. Команда FFmpeg:

```bash
ffmpeg -i input.mkv \
  -c:v libsvtav1 -preset 6 -crf 26 \
  -pix_fmt yuv420p10le \
  -svtav1-params "keyint=10s:tune=0:scd=1:film-grain=8" \
  -c:a libopus -b:a 112k -ac 2 \
  -movflags +faststart \
  output.mkv
```

Параметры:
- `crf 26` — визуально прозрачный для 1080p/4K живого контента (диапазон 24–28); для архивного качества 18–24【turn0search1】
- `preset 6` — лучшее соотношение качество/скорость на CPU【turn0search11】
- `yuv420p10le` — 10-bit обязательно: уменьшает бандинг в градиентах и тенях без замедления кодирования (5–20 % дельта)【turn2search6】【turn2search7】
- `film-grain=8` — синтез зерна: SVT-AV1 вычищает настоящее зерно и замещает его синтетическим, экономя 15–30 % битрейта на плёночном контенте【turn2search1】【turn0search3】
- `keyint=10s` — GOP 10 секунд, удобен для перемотки и стриминга【turn0search1】
- `libopus 112k` — прозрачен для стереомузыки при 96–128 kbps【turn0search7】

## Модуль 2: Максимальное сжатие (когда время не критично)

Для архивов, где важен каждый мегабайт:

```bash
ffmpeg -i input.mkv \
  -c:v libsvtav1 -preset 4 -crf 24 \
  -pix_fmt yuv420p10le \
  -svtav1-params "keyint=10s:tune=0:scd=1:film-grain=10:enable-overlays=1:scm=0" \
  -c:a libopus -b:a 128k -ac 2 \
  output.mkv
```

Переход с preset 6 на preset 4 даёт дополнительные ~2 пункта BD-rate (≈57 % против 55 % экономии), но кодирование замедляется примерно в 2,5 раза (с 11 до 4,5 fps на 1080p).【turn0search11】

## Модуль 3: GPU-ускорение (когда нужно «здесь и сейчас»)

Если есть RTX 40-й или 50-й серии (или Arc A-series / Battlemage):

```bash
ffmpeg -i input.mkv \
  -c:v av1_nvenc -preset p7 -tune hq -rc vbr -cq 28 \
  -b:v 0 -maxrate 8M -bufsize 16M \
  -pix_fmt p010le \
  -c:a libopus -b:a 128k \
  output.mkv
```

Скорость — сотни fps, но файл будет примерно на 15 % тяжелее, чем у SVT-AV1 preset 6 при том же VMAF. На RTX 50-й серии появился режим Ultra High Quality для сохранения зерна, но он пока не экспонирован в FFmpeg напрямую — нужен NVEnc от rigaya.【turn0search11】【turn0search10】

## Модуль 4: Автоматизация через Av1an / ab-av1

Если хочется «настроил и забыл» с целевым VMAF:

```bash
# ab-av1 — авто-поиск CRF под целевой VMAF (например, 95)
ab-av1 auto-encode -i input.mkv --preset 6 --min-vmaf 95 --crf-max 32 \
  -e libsvtav1 --pix-format yuv420p10le --vmaf-scale 1280x720 \
  -o output.mkv
```

ab-av1 кодирует короткие сэмплы, считает VMAF и бинарным поиском подбирает CRF под заданный порог качества, что избавляет от угадывания CRF для каждого источника.【turn0search10】【turn0search12】

Av1an — более продвинутая обёртка с распараллеливанием, поддержкой VapourSynth-фильтров и target-quality режимом.【turn2search3】

## «Без потери качества» — важное уточнение

Истинно лосслесс-режим (`-crf 0` / `--lossless`) у AV1 существует, но файл получится **больше**, чем у современного lossless-кодека вроде x265 lossless, и не даст экономии места. На практике все оптимизации по размеру работают за счёт **визуально прозрачного** сжатия (VMAF 95+), где артефакты неразличимы глазом, но битрейт уже существенно ниже исходного. Поэтому рабочее определение «без потери качества» в 2026 году — это CRF 22–26 при preset 4–6, что даёт VMAF 95–99 на большинстве контента.【turn0search1】【turn0search14】

## Контент-зависимые настройки

- **Аниме / 2D-мультфильмы**: `film-grain=4`, `crf 24–28`, можно добавить `tune=0` (VQ). Анимация хорошо сжимается плоской заливкой блоков, поэтому файлы получаются маленькими даже при низком CRF.【turn2search1】
- **Геймплей / скринкасты**: `film-grain=0` (зерна нет), `crf 26–30`, `preset 6–8`. Много статичных регионов — AV1 справляется отлично, но быстрые движения UI требуют чуть ниже CRF.
- **4K HDR**: `pix_fmt yuv420p12le`, `crf 22–26`, `preset 4–6`, обязательно `tune=0`. Для HDR-контента есть форк SVT-AV1-HDR с PQ-оптимизированной кривой и tune 3 для зерна.【turn2search3】
- **Плёночный контент с зерном**: `film-grain=10–15` критически важен — без него кодер либо сжигает битрейт на шум, либо размывает до «воскового» вида.【turn2search1】【turn0search3】

## Двухпроходное кодирование для фиксированного размера

CRF — режим постоянного качества, и размер файла заранее неизвестен. Если нужно попасть в конкретный объём (например, уложить фильм на флешку), используйте 2-pass VBR:

```bash
# Pass 1
ffmpeg -i input.mkv -c:v libsvtav1 -preset 6 -b:v 4M -pass 1 \
  -an -f null /dev/null
# Pass 2
ffmpeg -i input.mkv -c:v libsvtav1 -preset 6 -b:v 4M -pass 2 \
  -pix_fmt yuv420p10le -c:a libopus -b:a 128k output.mkv
```

В 2-pass кодер распределяет биты по сценам точнее, чем в CRF, но чуть медленнее и не даёт гарантий качества на сложных сценах. Для большинства задач CRF предпочтительнее.【turn0search16】

## Совместимость (что нужно держать в голове)

AV1 декодируется аппаратно примерно на 30–50 % устройств по состоянию на 2026 год: iPhone 15 Pro и новее, Mac на M3+, Samsung S23+, современные смарт-ТВ и GPU (RTX 30+, Arc, RDNA3+). На остальных устройствах работает программный декодер dav1d — на современном железе это незаметно, но на старых телефонах/ноутбуках жрёт батарею и CPU.【turn0search3】【turn2search9】【turn2search13】

Для файлов, которые должны проигрываться везде (старые ТВ, корпоративные ноутбуки), держите H.264-копию как fallback. Если совместимость не критична и нужен минимум места — AV1 безоговорочно.

# Зерно

`film-grain` в SVT-AV1 — это не отдельный фильтр шумоподавления и не классический денойз, который выкидывает зерно навсегда. Это встроенный в стандарт AV1 двухпроходный механизм: на стороне кодера зерно **анализируется и удаляется**, в битовый поток записываются **параметры модели зерна** (несколько десятков байт), а на стороне декодера зерно **синтезируется заново** из этих параметров и накладывается поверх декодированной картинки как пост-процессинг.【turn3fetch1】【turn3fetch0】

Главное отличие от обычного денойза — зерно не теряется, оно воспроизводится. Классический denoise-фильтр (hqdn3d, nlmeans, bm3d) вычищает шум и кодирует уже гладкую картинку — арт-намерение режиссёра исчезает, лица идут «пластиком». FGS же сохраняет визуальное присутствие зерна при минимальных затратах битрейта, потому что зерно не кодируется попиксельно, а описывается компактной математической моделью.【turn3fetch0】【turn3fetch1】

## Почему зерно — главный враг сжатия

Зерно случайно в пространстве и во времени: каждый пиксель и каждый кадр содержат независимый высокочастотный шум. Видеокодек работает на предсказании — ищет похожие блоки в соседних кадрах (motion compensation) и кодирует только разницу. На зерне предсказание ломается на каждом блоке: соседние кадры выглядят почти одинаково, но шум не совпадает нигде, и разница (residual) получается огромной.【turn2find1】

После DCT остаток распределяется по высокочастотным коэффициентам, которые обычно равны нулю и почти не стоят битов. Зерно делает их большими и ненулевыми, и квантователь вынужден либо кодировать их (дорого), либо обнулить — тогда зерно размазывается в «восковой» вид. Кольцевые фильтры кодека (CDEF, loop filter) дополнительно подавляют то, что похоже на шум. Результат: либо файл раздувается в разы, либо картинка деградирует.【turn3fetch1】

## Два шага FGS по стандарту AV1

**Шаг 1 — денойз и анализ (encoder side).** Кодер убирает зерно из исходных кадров и получает «чистую» версию. Стандарт AV1 не предписывает конкретный алгоритм денойза — годится любой адаптивный фильтр с компенсацией движения. Затем из разницы между зашумлённым и очищенным кадром оцениваются параметры зерна. Оценка ведётся только на плоских участках (небо, гладкие фоны), чтобы не путать зерно с краями и текстурами; края детектируются и исключаются из анализа.【turn3fetch1】

**Шаг 2 — синтез (decoder side).** Параметры модели передаются в битовый поток. Декодер раскодирует чистую картинку, затем генерирует зерно по модели и накладывает его поверх. Это обязательный этап декодирования AV1 — все совместимые декодеры (dav1d, libaom, аппаратные) обязаны его поддерживать, в отличие от опциональных SEI-сообщений H.264/H.265, которые большинство декодеров игнорирует.【turn3fetch1】

## Что именно моделируется

Параметры зерна описываются двумя компонентами:

- **Паттерн зерна** — авторегрессионная (AR) модель. AR-коэффициенты {a₀, a₁, a₂, a₃} захватывают пространственную корреляцию между сэмплами зерна и управляют его «крупностью»: грубое зерно киноплёнки 35 мм или мелкое цифровое — разные коэффициенты. Из них генерируется шаблон шума 64×64, из которого при воспроизведении нарезаются случайные патчи 32×32 и накладываются на кадр.【turn3fetch0】
- **Интенсивность зерна** — кусочно-линейная функция масштабирования, связывающая яркость пикселя с силой шума. Это критично: настоящее зерно в тенях ведёт себя не так, как на свету. Функция позволяет синтетическому зерну адаптироваться к яркости сцены, чтобы оно выглядело как оригинал, а не как однородный статический шум.【turn3fetch0】

В итоге в битовый поток попадают десятки байт на параметры вместо мегабит на попиксельное кодирование зерна.

## Как это выглядит в FFmpeg

Два параметра в `-svtav1-params` управляют всем процессом:

```bash
ffmpeg -i input.mkv \
  -c:v libsvtav1 -preset 6 -crf 26 \
  -pix_fmt yuv420p10le \
  -svtav1-params "tune=0:film-grain=8:film-grain-denoise=1" \
  -c:a libopus -b:a 112k \
  output.mkv
```

- **`film-grain=8`** — уровень анализа и моделирования зерна (диапазон 0–50). Отвечает за то, насколько aggressively кодер ищет и описывает зерно. 0 — FGS выключен.【turn2find1】
- **`film-grain-denoise=1`** — флаг, который говорит кодеру действительно удалить смоделированное зерно из кадров перед их кодированием. Без него кодер лишь добавляет синтетическое зерно поверх оригинального, которое осталось в кадре и дорого кодируется. Именно этот флаг даёт основную экономию битрейта на шумном контенте.【turn2find1】

По умолчанию FGS в SVT-AV1 выключен — если параметры не заданы, кодер ничего не делает с зерном и кодирует его попиксельно.【turn2find1】

## Рекомендуемые значения по типу контента

| Контент | `film-grain` | Пояснение |
|---|---|---|
| Живое кино с нормальным зерном | 8 | Стандартная отправная точка для плёночных источников |
| Тяжёлые плёночные сканы / зерно 16 мм | 10–15 | Агрессивнее вычищает и сильнее моделирует |
| 2D-анимация, чистый цифровой контент | 4–6 | Зерна мало, слишком высокий уровень навредит |
| Скринкасты, геймплей, презентации | 0 | Зерна нет, FGS не нужен — только добавит накладные расходы |
| HDR с зерном | 8–12 | Дополнительно — форк SVT-AV1-HDR с PQ-оптимизированной кривой |

Значения выше 15 стоит применять только к реально шумным сканам — иначе повышается риск артефактов синтеза.【turn2find1】

## На что обращать внимание при использовании FGS

**Метрики качества ненадёжны.** VMAF и PSNR сравнивают пиксели, а синтетическое зерно по определению не совпадает с оригинальным попиксельно. Метрика может «наказать» кадр, который выглядит правильно, и «поощрить» размытый, если он ближе к денойзенному референсу. Оценивать FGS можно только глазами: A/B-сравнение исходника и результата в плеере.【turn2find1】

**Три типичных проблемы при завышенном `film-grain`:**
- **Однородность** — синтетическое зерно выглядит одинаковым во всех участках, особенно в тенях, тогда как настоящее варьируется по яркости.
- **Мерцание** — зерно читается как анимированный статический шум, а не как текстура плёнки.
- **Пластиковые полутона** — если `film-grain-denoise` сработал слишком агрессивно, под синтетическим слоем лица идут «восковыми».【turn2find1】

При появлении артефактов уровень понижают на 2–4 пункта и прогоняют заново — на 60-секундном сэмпле это занимает минуты.【turn2find1】

**Не применять FGS на младших рунгах битрейт-лестницы.** На 240p после даунскейла зерна уже не остаётся, и анализ только тратит время. FGS включают на верхних рунгах, где зерно реально выживает.【turn2find1】

**Стоимость декодирования.** Синтез зерна — это дополнительная работа на стороне декодера, но dav1d и современные аппаратные декодеры справляются с ней эффективно. На очень старых или дешёвых устройствах стоит проверить перед массовым внедрением.【turn2find1】

## Почему просто не использовать внешний денойз перед кодированием

Можно — например, `ffmpeg -vf hqdn3d` или `nlmeans` до SVT-AV1. Но это необратимо уберёт зерно, и декодер не вернёт его при воспроизведении. Картинка станет чище, файл — меньше, но потеряется арт-намерение: зерно в кино часто выбрано режиссёром сознательно, и его устранение меняет восприятие сцены.【turn3fetch1】

FGS решает ровно ту же задачу экономии битрейта, что и внешний денойз, но сохраняет зрение зерна — за счёт того, что оно восстанавливается из компактной модели. Netflix включил FGS в продакшн именно ради этого: значительная экономия битрейта при сохранении художественной целостности плёночного зерна, проверенная на миллионах стримов.【turn3fetch0】

Иными словами, `film-grain` в SVT-AV1 — это не «третий фильтр денойза поверх двух других», а встроенный в кодек механизм «вырезать → описать параметрами → восстановить при просмотре», который делает возможным то, что классический денойз не делает: маленький файл с живым зерном.



Денойз внешним фильтром целесообразен в основном для **лайв-экшна с реальным зерном** и **частично для старого аниме с сильным BD-зерном**; для чистого цифрового аниме он редко нужен, а для 3D-рендеров почти всегда избыточен. Связка **BM3D (bm3dcuda) + SMDegrain(tr=1)** с авто-подбором sigma через YDIF — действительно одна из лучших конфигураций 2026 года для живого видео по балансу качество/скорость, но «топ» она не универсален: на аниме BM3D может портить линии, на 3D-рендерах он не нужен в принципе.【turn0fetch0】【turn3search0】【turn4search4】

## Целесообразность денойза по типам контента

| Тип контента | Нужен ли денойз | Почему | Рекомендуемый фильтр |
|---|---|---|---|
| **Лайв-экшн, плёночное зерно** | Да, если зерно тяжёлое и FGS не справляется | Реальное зерно дорого кодируется; FGS AV1 моделирует его компактно, но для крупного/анимированного зерна модель неточна — внешний денойз даёт дополнительную экономию | BM3D + SMDegrain, sigma 4–8 |
| **Лайв-экшн, чистый цифровой (RED, Alexa)** | Редко | Шума почти нет; FGS на низком уровне (film-grain=4–6) или вообще без него | FGS AV1, внешний не нужен |
| **Аниме, старое (BD-ремастер с зерном)** | Иногда | Студийное зерно от ремастера съедает битрейт; но линии хрупкие | KNLMeansCL предпочтительнее BM3D |
| **Аниме, современное цифровое** | Почти никогда | Фоновое зерно добавлено для анти-бандинга; в 10-bit бандинг и так подавлен, зеро лишь раздувает файл | Лёгкий SMDegrain(tr=1) или FGS=4 |
| **3D-рендер (Cycles, Redshift, V-Ray)** | Нет | Источник уже денойзирован встроенным ИИ-денойзером рендера (OptiX/OIDN/Corona); пост-денойз только размывает детали | Не применять |

## Почему для каждого типа так

### Лайв-экшн — основной кейс для денойза

Плёночное зерно — случайный высокочастотный шум, который ломает motion prediction кодека на каждом блоке. AV1 FGS решает это через модель «вырезать → описать параметрами → восстановить», но модель AR-типа (64×64 шаблон) хорошо описывает **мелкое статичное** зерно, а крупное анимированное или смешанное с компрессионными артефактами моделирует неточно — синтетическое зерно «мерцает» или выглядит однородным.【turn4search12】【turn4search13】

Внешний денойз здесь работает как «тяжёлая артиллерия»: убирает зерно физически, оставляя кодеру чистую картинку. Экономия может достигать 30–50 % битрейта на зернистом источнике. Минус — потеря арт-намерения режиссёра, поэтому для архива с художественным зерном лучше комбинировать: слабый денойз (BM3D sigma 2–4) для подавления самого случайного шума + FGS film-grain=8 для восстановления текстуры зерна из модели.【turn0fetch0】【turn4search10】

### Аниме — BM3D работает, но с риском для линий

В аниме зерно обычно фоновое, добавленное студией для анти-бандинга или текстуры. На современных цифровых сериалах его почти нет, и денойз избыточен — в 10-bit бандинг подавлен и без зерна.【turn0fetch0】

Когда денойз нужен (старые BD-ремастеры с сильным зерном, VHS-рипы, компрессированные источники), выбор фильтра критичен. **BM3D на аниме может портить lineart**: алгоритм block-matching ищет похожие патчи, а в аниме плоские заливки соседствуют с тонкими контурами — BM3D размывает края или создаёт «ступеньки» на линиях. KNLMeansCL (NLMeans на GPU) лучше сохраняет линии, потому что работает в пространстве патчей без агрессивной реконструкции, и исторически рекомендуется для аниме.【turn0fetch0】【turn1search7】

SMDegrain (темпоральный, на MVTools) на аниме даёт другой риск — **chroma smearing** при обработке цветовых плоскостей, что может «размазать» движущиеся контуры. Решение — обрабатывать только luma, а хрому отдельно пространственным фильтром.【turn0fetch0】

### 3D-рендер — денойз уже сделан внутри рендера

Современные 3D-движки (Blender Cycles, Redshift, V-Ray, Corona, Octane) используют path tracing и имеют **встроенные ИИ-денойзеры**: NVIDIA OptiX, Intel OIDN, Corona Denoiser. Они работают во время рендера, используют буферы нормалей/深度/AOV и убирают шум умнее, чем любой пост-фильтр, потому что видят геометрию сцены.【turn4search4】【turn4search7】

Если финальный кадр шумный — это значит, что рендер сделан с малым числом сэмплов без включения денойзера. Правильное решение — поднять сэмплы или включить встроенный денойз в рендере, а не применять BM3D к уже готовому кадру. BM3D на 3D-рендере размоет тонкие текстуры и нормали-границы, которые рендер аккуратно сохранил, и не вернёт деталей, которые не были отрендерены.【turn4search4】

Исключение — если 3D-рендер сохранён в lossless и потом пережат с потерями, появились блоки/бандинг. Тогда лёгкий денойз уместен, но это уже реставрация артефактов сжатия, а не удаление зерна.

## Является ли BM3D + SMDegrain топом в 2026 году

Коротко: **да, для живого видео с классическим шумом — это одна из лучших связок по соотношению качество/скорость**, но не безоговорочный «топ» во всех сценариях.

### Что в связке хорошо

**BM3D как primary spatial денойзер.** Это классический state-of-the-art алгоритм для гауссова шума, и в 2026 году он остаётся эталоном по сохранению деталей при заданном уровне подавления шума. Качество выше, чем у dfttest/FFT3D и KNLMeansCL на одинаковом sigma, при условии правильной настройки.【turn0fetch0】【turn3search0】

**GPU-ускорение через bm3dcuda.** На NVIDIA T4/RTX-классе: 1080p, radius=1, fast=True — ~38+ fps; radius=3, fast=True — ~22 fps. Это скорость, сопоставимая с реальным временем, чего не было у CPU-версии BM3D (1–5 fps).【turn1search13】【turn0search10】 Скорость превращает BM3D из «только для энтузиастов» в production-инструмент.

**SMDegrain(tr=1) как лёгкий темпоральный проход.** Компенсирует слабость BM3D на темпоральной оси: BM3D (даже V-BM3D с radius=1) слабо использует межкадровую избыточность для подавления мерцающего шума. SMDegrain с малым radiusом добавляет темпоральное сглаживание почти бесплатно по скорости и без сильного размывания.【turn0fetch0】

**Связка через ref-параметр.** Документация BM3D явно поддерживает схему «SMDegrain как basic estimate, V-BM3D как final estimate» — это компенсирует недостатки обоих: SMDegrain эффективен для темпорального сглаживания, но даёт blending и потерю деталей; V-BM3D хорошо сохраняет детали, но слаб на крупный шум. Комбинация даёт лучшее из двух.【turn0fetch0】

**Авто-подбор sigma через YDIF.** YDIF (median absolute difference между соседними кадрами) — стандартная оценка уровня шума; `sigma_from_ydif` даёт разумный автоматический режим, не требующий ручного тюнинга для каждого источника. Это критично для пайплайнов «кинул папку — получил результат». Порог YDIF задаётся отдельно для каждого типа контента в настройках (`denoise_threshold_animation/liveaction/rendered`); значение `-1` = денойз выключен для этого типа. Дефолты: аниме и 3D-рендер = 3.0, живое видео = выключено.

### Где связка не топ

**Аниме с линиями.** BM3D может разрушать тонкие контуры — для аниме чаще предпочитают KNLMeansCL (GPU NLMeans), который мягче на краях, или комбинацию KNLMeansCL + слабый SMDegrain.【turn0fetch0】【turn1search7】

**Тяжёлый шум с большими паттернами.** BM3D (и даже V-BM3D) слаб на крупное зерно 16-мм плёнки или сильно компрессированный шум. Здесь теоретически сильнее **V-BM4D** — 4D-расширение, группирующее spatio-temporal объёмы вместо блоков. Но готового production-плагина V-BM4D для VapourSynth нет, а CPU-реализации непрактично медленные.【turn1search10】【turn1search13】

**Реальный негауссов шум (сенсорный, компрессионный).** Нейросетевые денойзеры (SCUNet, NAFNet, Real-ESRGAN в режиме denoise) превзошли BM3D на реальных сложных шумах по метрикам качества — они обучены на реальных degradation, а не на модельном гауссовом шуме.【turn1search4】【turn1search1】 Проблема: зрелых видео-плагинов VapourSynth для этих сетей нет, а покадровые прогоны через Waifu2x/Real-ESRGAN дают ≤1 fps даже на GPU, что непрактично для видео-пайплайнов.【turn0fetch0】

**3D-рендер.** Здесь BM3D не нужен — встроенные денойзеры рендера (OptiX, OIDN) работают лучше, потому что имеют доступ к геометрии сцены.【turn4search4】

### Альтернативы для справки

| Фильтр | Тип | Скорость (1080p) | Качество | Кейс |
|---|---|---|---|---|
| **bm3dcuda** (GPU) | spatial+temporal | 22–40 fps | Очень высокое | Лайв-экшн, классический шум |
| **KNLMeansCL** (GPU) | spatial+temporal | 20–50 fps | Высокое, сохраняет линии | Аниме, старое видео |
| **SMDegrain** (CPU) | temporal | 10–30 fps | Среднее, мягкий | Лёгкая темпоральная очистка |
| **FFT3DGPU** | freq-domain | 30+ fps | Среднее | Быстрая грубая очистка |
| **V-BM4D** | 4D spatio-temporal | <1 fps (CPU) | Очень высокое | Тяжёлый шум (нет GPU-плагина VS) |
| **Real-ESRGAN/NAFNet** | neural | ≤1 fps (per-frame) | Высочайшее на реальном шуме | Реставрация, не для видео-пайплайна |

## Итоговая рекомендация

Для пайплайна «минимум времени, минимум веса»:

- **Лайв-экшн**: связка bm3dcuda + SMDegrain(tr=1) с авто-sigma через YDIF — отличный выбор. После денойза подавать в SVT-AV1 с film-grain=4–6 (лёгкий FGS для восстановления текстуры) — получишь минимальный файл с визуально приятной картинкой.
- **Аниме**: заменять BM3D на KNLMeansCL (h=0.4–0.6, d=1–2) для сохранения линий, SMDegrain(tr=1) оставить как лёгкий темпоральный проход. Для чистого цифрового аниме — пропускать денойз, сразу FGS film-grain=4.
- **3D-рендер**: не денойзить внешним фильтром. Убедиться, что в рендере включён OptiX/OIDN, сэмплы достаточно высоки. Кодировать SVT-AV1 с film-grain=0 — зёрна нет, FGS не нужен.

Связка текущая — рабочая и в 2026 году актуальная, но «топ» именно для живого видео с зерном. На аниме её стоит модифицировать (BM3D → KNLMeansCL), на 3D-рендере — не применять вовсе.
